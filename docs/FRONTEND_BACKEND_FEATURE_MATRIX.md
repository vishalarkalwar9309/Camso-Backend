## 1. Overview & Verification Status Taxonomy

This document establishes 1-to-1 traceability between every user-facing Flutter screen, interaction, button, form, filter, and role gate in `Frontend`, and the corresponding Express routes, Prisma models, controllers, services, repositories, and automated test suites in `camso-backend`.

### Verification Status Classification:
- **`IMPLEMENTED — VERIFIED E2E`**: Feature is fully connected from the Flutter UI screen/repository to the real backend HTTP endpoint. Validated across three tiers:
  1. **Unit-tested**: Flutter unit/widget tests (`flutter test`) and backend unit/integration tests (`jest`).
  2. **Integration-tested against a real backend**: Live HTTP smoke tests against `http://localhost:4000` with real database queries, mutations, role authorization, and validation schemas.
  3. **Browser/runtime-tested**: Compiled with `flutter build web --no-pub` and verified active and interactive in browser session.
- **`CLIENT-SIDE COMPUTED — VERIFIED`**: Self-contained mathematical calculation or client action; verified with unit/widget tests.
- **`BLOCKED BY CONFIGURATION`**: Feature logic and fallbacks are implemented and verified in code, but physical delivery requires external third-party production credentials (specifically: physical iOS/Android FCM push delivery requires hardware devices and production FCM service account keys; real Cloud Storage requires production Firebase Storage bucket permissions).
- **`NOT TESTED / EXCLUDED`**: Production continuous deployment pipelines or external physical device push testing not applicable to local development environments.
